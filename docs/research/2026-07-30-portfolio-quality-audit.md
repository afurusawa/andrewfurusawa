# Portfolio quality audit beyond performance

**Issue:** [#4](https://github.com/afurusawa/andrewfurusawa/issues/4)  
**Audited:** 2026-07-30  
**Scope:** the public home page; accessibility, SEO, security/dependency hygiene, responsive/theme behaviour, and content/link correctness. This is a source audit, not an implementation change.

## Evidence and limitation

`Resolve-DnsName` and an HTTPS request for `andrewfurusawa.com` both failed with a name-resolution error on the audit host. The live page, its HTTP headers, rendered DOM, mobile layout, contrast, and third-party profile links therefore could not be independently tested. Findings labelled **local-code evidence** come from the checked-out source; findings labelled **production confirmation required** must be retested after DNS is restored.

The checked-out production dependency lockfile is `next@15.3.3`. `npm audit --omit=dev --json` reported one critical and two high-severity production dependency entries (`next`, transitive `postcss`, and transitive `sharp`), with a non-major fix available at `next@15.5.22`. The audit report lists a critical Next React Flight RCE advisory among the affected advisories: [GHSA-9qr9-h5gf-34mp](https://github.com/advisories/GHSA-9qr9-h5gf-34mp). npm documents that `npm audit` asks the registry for known-vulnerability reports; its output is time-sensitive and should be rerun when the update is made ([npm audit documentation](https://docs.npmjs.com/auditing-package-dependencies-for-security-vulnerabilities/)).

## Production validation addendum — `andrewfurusawa.dev`

The availability limitation above applied to the former `.com` domain and is now superseded. On 2026-07-30, the canonical `https://andrewfurusawa.dev/` returned HTTPS 200 from Vercel, and `www.andrewfurusawa.dev` returned a 307 redirect to the apex. The rendered page title, description, and content matched the repository.

- Only `Strict-Transport-Security` was present among the checked CSP, content-type, frame, referrer, permissions, and cross-origin headers. `robots.txt` and `sitemap.xml` both returned 404.
- The browser accessibility tree confirmed that the theme button and hero GitHub/LinkedIn links have empty accessible names; the skills filter is named only by its `FILTER` placeholder. The theme button has neither `aria-label` nor `aria-pressed`.
- At 320 px and 375 px CSS viewports, the document width was 490 px, confirming horizontal overflow. At 768 px and 1280 px there was no overflow.
- In the live skills filter, querying `react` returned React and ReactiveX; replacing that query with `angular` returned no results, confirming that filtering the previous result set loses skills that should be restored.
- The regenerated lockfile's current production-only audit still reports 1 critical and 2 high vulnerabilities. The deployment serves the older Next.js build, so it must be upgraded and redeployed before this can close as remediated.

## Findings, priority order

| Priority | Area | Finding | Evidence and effect | Required remediation / acceptance check |
| --- | --- | --- | --- | --- |
| P0 | Availability | The canonical production domain is not resolvable from the audit environment. | **Production evidence:** DNS A lookup and `https://andrewfurusawa.com` request both failed to resolve. A site that cannot resolve cannot be crawled, loaded, or audited. | Restore the intended apex and `www` DNS/hosting configuration; verify an HTTPS `200` or intentional redirect from independent networks, a valid certificate, and the expected canonical host before closing the quality work. |
| P0 | Security / dependencies | The locked Next.js version is within reported critical and high advisory ranges. | **Local-code evidence:** `package-lock.json` resolves `next@15.3.3`; the production-only npm audit reports 1 critical and 2 high dependency entries, with `next@15.5.22` as its safe non-major fix. This is material even for a small portfolio because the framework is exposed by the deployed server. | Upgrade and lock to at least the audit-provided fixed release (or a newer supported release), deploy it, and record fresh `npm audit --omit=dev` results with no high/critical findings. Rebuild and smoke-test the deployed page. Enable Dependabot alerts/security updates; GitHub says those alerts identify known vulnerable dependencies and their fixed versions ([GitHub Docs](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-alerts)). |
| P1 | Accessibility | The theme button and the two hero social links are icon-only controls without explicit accessible names. | **Local-code evidence:** `ThemeToggle.tsx` renders a button containing only `FaSun`/`FaMoon`; `page.tsx` renders icon-only anchors to `https://github.com` and `https://linkedin.com`. All interactive controls need useful names; W3C recommends native visible labels where possible and identifies `aria-label` as a valid naming technique when visible text is not appropriate ([W3C WAI](https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/)). | Give the control an accurate name and state, e.g. `aria-label="Switch to dark theme"` plus `aria-pressed`, and label social links with their destination. Hide purely decorative icon SVGs from assistive technology. Test keyboard and screen-reader announcements. |
| P1 | Accessibility | The skills filter uses `placeholder="FILTER"` but has no persistent visible or programmatic label; its focus outline is removed without a replacement. | **Local-code evidence:** `SkillsSection.tsx` contains an unlabeled text input; `globals.css` applies `focus:outline-none` and does not add a focus-visible replacement. W3C says labels should identify form controls, and a placeholder is only a fallback—not a substitute for a label ([W3C labels tutorial](https://www.w3.org/WAI/tutorials/forms/labels/); [W3C accessible-name guidance](https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/)). | Provide a visible `label` (or visually hidden label with an intentional accessible name) and an unmistakable `:focus-visible` treatment meeting contrast expectations. Keyboard test Tab/Shift+Tab in both themes. |
| P1 | Accessibility | The background animates automatically and indefinitely, with neither a user control nor a reduced-motion rule. | **Local-code evidence:** `.animate-swirl` runs a 15-second infinite animation; no `prefers-reduced-motion` rule or pause/hide control exists. WCAG 2.2.2 requires a way to pause, stop, or hide non-essential motion that starts automatically, lasts more than five seconds, and appears alongside other content ([W3C explanation](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide)). | Respect `prefers-reduced-motion: reduce` by disabling the animation, and either add a persistent pause/hide mechanism or establish that the visual is exempt after an accessibility review. Verify with the OS reduced-motion preference enabled. |
| P1 | Responsive / theme | The layout has large fixed mobile padding and an unwrapped hero row, creating a high risk of horizontal overflow and cramped content on narrow screens. | **Local-code evidence:** both `main` and the page container use `p-16` (64 px each side); the hero places a `text-4xl` heading and two icons in a `flex` row without `flex-wrap`; `h1` is `text-7xl`. There are no responsive variants in the rendered home-page components. | At 320, 375, 768, and 1280 CSS px, confirm no horizontal scrolling, no clipped controls, readable line lengths, and usable tap/focus targets in both themes. Use responsive padding/type and wrap/stack the hero as needed. |
| P1 | SEO / discoverability | The site has basic title, description, language, icon, and `metadataBase`, but lacks explicit canonical, social-preview, robots, and sitemap metadata. | **Local-code evidence:** `layout.tsx` supplies only title and description; there is no `app/robots.*`, `app/sitemap.*`, canonical, Open Graph, or Twitter metadata. Google recommends clear, unique titles/descriptions and says a sitemap can be submitted to help discovery ([Google SEO Starter Guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)); Next supports `robots` and sitemap metadata file conventions ([Next.js robots documentation](https://nextjs.org/docs/app/api-reference/file-conventions/metadata/robots)). | Once production is reachable, inspect the served `<head>`, `/robots.txt`, and `/sitemap.xml`. Add explicit canonical and share metadata, robots, and a single-page sitemap where consistent with the chosen canonical host. Validate with Search Console URL Inspection and a social-card debugger. |
| P1 | Security headers | No application-level security-header policy is configured. | **Local-code evidence:** `next.config.ts` has no `headers()` configuration. The hosting platform might add headers, but that cannot be verified while DNS is down. | Define headers at the host or application boundary and verify them in production: a CSP compatible with the app, `X-Content-Type-Options: nosniff`, a restrictive frame policy (`frame-ancestors` or `X-Frame-Options`), a deliberate referrer policy, permissions policy, and HSTS only on the HTTPS canonical host. Next supports configuring response headers in `next.config.js` ([Next.js documentation](https://nextjs.org/docs/app/api-reference/config/next-config-js/headers)). |
| P2 | Content / links | The prominent hero icons link to generic GitHub and LinkedIn home pages, while the contact links point to the intended profiles. The page therefore sends users to the wrong destination from its first social controls. | **Local-code evidence:** `page.tsx` uses `https://github.com` and `https://linkedin.com`; `ContactSection.tsx` uses `https://github.com/afurusawa` and `https://linkedin.com/in/afurusawa`. GitHub and the GitHub profile returned 200 during this audit; LinkedIn returned 403 to this automated client, so its profile must be checked manually. | Point every personal social link to the verified personal profile, give it descriptive text/name, and manually open all `mailto:` and external links from the restored production page. |
| P2 | Content / semantics | Experience content exists but is never rendered; the visible page leads from an `h1` directly to an `h3`, and the only `<nav>` is empty. | **Local-code evidence:** `ExperienceSection.tsx` is not imported by `page.tsx`; the hero uses `h3` for "Front-End Developer" before the page's first `h2`; `page.tsx` renders an empty `<nav>`. The missing experience/projects makes the "12 years" claim difficult for a recruiter to assess. | Decide whether to publish verified experience/projects or remove the unused component. Use a logical heading hierarchy and remove the empty landmark. After content review, check that all career claims, employer names, dates, and destinations are accurate. |
| P2 | Theme behaviour | Theme preference is only applied after client hydration and ignores the system preference. | **Local-code evidence:** `ThemeToggle.tsx` starts in light mode and reads `localStorage` in `useEffect`, which can flash light for a returning dark-mode visitor; it does not query `prefers-color-scheme`. | Make the initial rendered theme intentional (no flash), retain an accessible explicit toggle, and test first visit, persisted light/dark preference, JavaScript-disabled fallback, and system light/dark preference. |
| P2 | Functional correctness | Skill filtering is stateful in a way that can lose results while the user edits the query. | **Local-code evidence:** `handleFilterSkills` filters the current `skills` array rather than immutable `data`; changing "react" to "angular" incrementally may never reintroduce Angular after it was filtered out. | Derive filtered results from the original data and current query, then test deletion, replacement, case changes, no matches, and keyboard use. |

## Positive evidence

- The root document has `lang="en"`, a single `h1`, basic title/description metadata, a favicon, and a main landmark.
- Contact/footer links that deliberately open a new tab include `rel="noopener noreferrer"`.
- Fonts are declared through `next/font/google`, which is a sound basis for avoiding render-time third-party font requests; performance validation belongs to the separate performance audit.

## Closure gate for issue #4

Do not close based on source changes alone. Closure requires:

1. DNS/HTTPS availability restored and the canonical host recorded.
2. A fresh production dependency audit and deployed framework update with no high/critical findings.
3. Keyboard and screen-reader checks of icon controls, filter label/focus, heading/landmark structure, and motion preference in both themes.
4. Mobile/desktop visual checks at 320, 375, 768, and 1280 px with no overflow or clipped controls.
5. Production checks for canonical/robots/sitemap/social metadata, security headers, personal links, and current portfolio claims.
6. A scheduled regression baseline: dependency alerts, accessibility lint/automated audit, link checking, and real-user/uptime monitoring as agreed in the wayfinder scope.
